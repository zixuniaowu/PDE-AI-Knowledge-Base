## 背景

定型実装・テストコードは時間がかかるが創造性は低い。逆に、設計判断は創造的だが AI に任せられない。この非対称を利用する。

## 人間の役割

- 設計判断・アーキテクチャ決定
- 生成コードの理解と採否。**理解できないコードはマージしない**
- 境界条件・セキュリティ（認証・認可・入力検証）の実装と確認

## AI の役割

- 関数・モジュール単位の実装たたき台生成
- テストケース一覧（境界値・異常系）とテストコードの生成
- 型・規約に沿った修正案の提示
- 既存コードベースを踏まえた実装箇所の提案（RAG）

## プロンプト例

```text
あなたはこのリポジトリの実装補助です。以下の仕様を実装してください。
条件:
・既存のヘルパー関数を再利用する（新規に作る前に src/utils を検索）
・テストコードも生成する（正常系2、境界値2、異常系2）
・出力は {files: [{path, code}], tests: [{name, code}], assumptions: []} 形式
・判断に迷った点は assumptions に列挙し、勝手に決めない
仕様: （記入） 関連設計書: （添付）
```

## 失敗パターン

- 存在しない API・ライブラリ関数を生成する → バージョンを固定して伝え、利用 API の実在を CI で保証
- テストが「常に通る空テスト」になる → アサーションの存在をコードレビューで必ず確認
- 巨大 diff でレビュー不能になる → 関数単位で小さく依頼し、PR も小さく切る

## 効果の測り方

- 定型実装の工数（導入前後比較）
- 生成コードの採用率・修正量
- 不具合率が上がっていないか（リリース後の欠陥数）

## 法規・保存・正本・決裁

- 根拠法規: 著作権法（生成コードのライセンス汚染確認）。顧客案件では契約上のコード納品範囲
- 保存期間: コード・レビュー記録はリポジトリに永続。生成物の採否理由も PR に残す
- 正本システム: コードの正本はリポジトリ。AI 生成物は必ず PR 経由で入り、直接 push しない
- 決裁者: マージはレビューアー。認証・金銭系はテックリードの行単位確認を追加で必須

コストの試算方法は[コスト見積もり](/references/cost-estimate.md)を参照。

## FDE 実装メモ

- ツール構成: Claude Code / Cursor に関数単位で依頼（{files, tests, assumptions} 契約）→ 人間が全行レビュー → テスト生成 → PR
- 連携: リポジトリ直結。設計書の該当セクションを毎回コンテキストに渡す
- 制約: 1 PR 400 行以内。理解できない行はマージ不可
