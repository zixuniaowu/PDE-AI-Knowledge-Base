## この工程の目的

リファインメントは「チケットを書く作業」ではない。**「まだ実行できないものを実行できる形に磨く」継続活動**である。判定基準は単純: 上位のバックログ項目が「明日朝一で誰かが着手できるか」。できないなら粒度・AC・依存のどこかが欠けている。

- **インプット: ** 生の要望（声・メール・会議メモ）、プロダクトの状況データ
- **アウトプット**: Ready 状態のストーリー（粒度適正 / AC 付き / 依存明示 / 見積もり済み）
- **この活動が失敗したとき**: プランニングで曖昧なものを引いて見積もりが 2 倍外れ、スプリントが毎回破綻する。**プランニングの質は 2 週間前のリファインメントで決まっている**

## この活動特有の失敗（AI 以前からある問題）

1. **巨大ストーリーの放置**: 「決済機能を作る」。分割されないまま 3 か月先送りされる
2. **AC がない / 曖昧 AC**: 「ちゃんと動くこと」。テストにも検収にも使えない
3. **重複と腐敗**: 同じ要望が 3 形式で 3 件。実装済みの項目が残り続ける
4. **実装の詳細まで書き込む**: How まで書いたストーリーは、実装者の手を縛りすぐ古くなる
5. **備考欄化**: 書いた人が誰も戻らない墓場

## 人間の役割

- **価値の判断と優先順位**: これをやる意味があるか、今やる意味があるか。AI に判断できない
- **粒度の最終決定**: 分割の切れ目（どこで価値として独立するか）はドメインとチームの知識
- **要望の背景の聞き取り**: 「検索が欲しい」の背後が「データが見つからなくて困っている」なら、解は検索とは限らない

## AIの役割

- 曖昧語・AC 欠落・巨大すぎるストーリーの検出
- AC ドラフトの生成（Given / When / Then 形式）
- 分割案の提示（価値の独立した単位での）
- 重複・実装済み・依存未解消ストーリーの検出（バックログ全体の横断チェック）
- 過去ストーリーとの類似性指摘（見積もりの参考、過去の実績時間）

## 協働の進め方（実プロンプト付き）

### 定期（週次）: バックログの健康診断

```text
あなたはプロダクトオーナーの補助です。添付のバックログを健康診断してください。
各項目をチェック: ①AC の有無と曖昧さ ②着手可能な粒度か（1 スプリント以内） ③依存の明示 ④他項目との重複 ⑤過去の完了ストーリーとの重複（実装済みなら削除候補）
出力: 表（項目 / 判定 / 問題 / 改善案）+ 今週のリファインメントで優先的に扱うべき 3 項目
```

### 個別: 巨大ストーリーの分割

```text
次のストーリーを、それぞれ独立に価値を提供できる単位に分割してください。
「顧客データのインポート機能を作る」
分割の制約: ①各分割が単体でユーザー価値を持つこと（技術的な層での分割禁止） ②各分割に AC ドラフト（Given/When/Then）を付ける ③最初にやるべき最小の分割を推奨する
```

### AC の質の担保

```text
この AC をテスト設計者の視点で批判してください。
「ユーザーはレポートをダウンロードできる」
・「ダウンロードできる」の検証方法は?（ファイルが壊れていなければ OK?）
・件数・形式・文字コードの条件は?
・失敗時（0 件、タイムアウト）の期待結果は?
批判に基づき、検証可能な AC に書き直してください。
```

## 成果物と受け入れ基準

- Ready 状態のストーリー（将来 2 スプリント分）

受け入れ基準:

- [ ] 上位 2 スプリント分の項目が全て AC 付き（Given/When/Then か同等の検証可能な形）
- [ ] 各項目の見積もりが済んでいる（または外れた理由が記録されている）
- [ ] 依存関係が明示されている
- [ ] 重複・実装済み項目がクローズされている
- [ ] 実装方法（How）は書いていない。What と検証条件だけ

## 工程間の受け渡しで壊れること

- **プランニングへ**: Ready でない項目をプランニングに流すと、見積もりが当てにならずコミットが破綻する。「Ready の定義」をチームで持つ
- **デイリーへ**: AC がない項目に着手すると、デイリーで「もうできた?」が判断できない。着手前に AC 確認を習慣化する
- **レトロへ**: 見積もり外れの分析には「見積もり時の前提」が必要。AC と前提を残しておく
