## この工程の目的

アジャイルのレビューには 2 つの顔がある。**PR レビュー**（コードの品質ゲート）と**スプリントレビュー**（成果物の価値確認）——両方に共通する目的は「次に進めてよいかを、証拠に基づいて判断する」こと。承認ハンコの式ではなく、判断のための時間である。

- **インプット**: 完成した PR / 増分、AC、受け入れ基準、利用者の声
- **アウトプット**: 承認（または却下と理由）、レビューコメントと対応の記録、スプリントレビューなら次へのフィードバック
- **この工程が失敗したとき**: 「AI が見たから OK」で品質ゲートが崩壊する。または逆に、全員が細部を指摘し合い価値判断の時間が消える

## この工程特有の失敗（AI 時代に加速した問題）

1. **AI 指摘の鵜呑み**: もっともらしいが設計意図に反する修正が通る
2. **レビュー不能な巨大 PR**: AI 生成で diff が肥大化。結果「一応見た」で承認される
3. **承認の形骸化**: 毎回全員 OK のチェックポイントは、実は誰も見ていない
4. **指摘の無限ループ**: 好みの擦り合わせに時間を溶かす
5. **スプリントレビューのデモ会化**: 良い点だけ見せて、価値の確認（これは必要だったのか?）をしない

## 人間の役割

- **設計・業務適合の判断**: この変更が正しい方向か。AC を満たしているか。テストが通っているかの先にある「価値」の判断は人間
- **セキュリティ・金銭・権限系の精査**: AI 指摘があっても 2 次確認を省略しない
- **指摘の採否と理由の記録**: 不採用の指摘には理由を残す。これが次回の AI チェックリストの改良材料
- **PR 作成者との対話**: 指摘の意図を伝え、学ばせる。レビューは人を育てる場でもある

## AIの役割

- 規約・命名・明らかなバグの機械的指摘（規約文書を引用して）
- diff 要約・影響範囲の推定（呼び出し元・依存モジュール）
- テストカバレッジの不足指摘・テストコード下書き
- 指摘への修正案の生成
- PR の「理解しにくい箇所」の検出（読み手視点）

## 協働の進め方（実プロンプト付き）

### PR 作成時: セルフレビューを AI に先にやらせる

```text
あなたはレビューアーの代行として、この PR をレビューしてください。
①変更要約 3 行 ②コーディング規約違反（規約を引用して指摘） ③影響が及びそうなモジュール ④不足していそうなテスト ⑤「読み手が理解しにくい箇所」
ルール: 設計の好みの指摘はしない。根拠のない指摘はしない。各指摘にファイル名と行番号を付ける。
diff: （添付） 規約: （添付）
```

### 人間のレビュー: AI の指摘は一次ふるいと割り切る

レビューアーは AI 指摘を「確認済み」として流し、**設計・価値・セキュリティの判断に時間を使う**。各指摘に採否を付け、不採用は理由を 1 行残す:

> 不採用理由例: 「ユーティリティ分離の指摘 → 本 PR スコープ外。リファインメントで管理」

### 修正対応も AI と対話で

```text
レビューコメントへの修正案を 2 パターン出してください。
パターン A: 指摘どおりに直す場合の diff
パターン B: 指摘への対処を別の方法で満たす場合の diff
指摘: （貼付） 該当コード: （貼付）
```

### スプリントレビュー: 価値の確認

```text
スプリントレビューの議事録テンプレートを準備してください。
①ゴールは達成されたか（証拠つき） ②利用者フィードバックの記録欄 ③「これは要らなかった」となったもの ④次スプリントへの持ち込み候補
※デモの成功譚ではなく、価値判断の記録を残す構成にする
```

## 成果物と受け入れ基準

- マージされた PR、レビュー記録（採否と理由付き）、スプリントレビュー記録

受け入れ基準:

- [ ] 少なくとも 1 名の人間がレビューし、承認している（名前の記録）
- [ ] テストが自動実行され、全て通っている
- [ ] AI 指摘のうち不採用のものに理由がある
- [ ] PR の diff はレビュー可能な大きさ（目安 400 行以内、超える場合は分割）
- [ ] セキュリティ・金銭・権限に関わる差分は人間が行単位で確認した
- [ ] スプリントレビューで「価値の確認（要らなかったものを認める）」が行われている

## 工程間の受け渡しで壊れること

- **リファインメント ←（逆方向）**: 「レビューで毎回同じ指摘」が出るなら、それはストーリーに最初から書くべきだった AC・制約。チェックリスト化してリファインメントに戻す
- **レトロへ**: レビューの滞留時間・不採用指摘の統計は、レビュー負荷の設計（AI への委譲範囲）を見直す材料
