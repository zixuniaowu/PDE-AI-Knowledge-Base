## この工程の目的

PDE のリリースは「デプロイボタンを押す」ことではなく、**「知られた形で世界に出し、壊れたときに戻れる状態を作る」こと**である。一人で作ると「自分だけが使えればいい」でも済む——だが PDE の価値は他人が使って初めて生まれる。初めての他人のアクセスが本番初日になる、という設計漏れを絶対に作らない。

- **インプット**: テスト済みのビルド、ドメイン・ホスティング設定、利用者への説明（最低限の案内）
- **アウトプット**: 公開 URL、動作確認の記録、既知問題の明示、フィードバックの受け皿（フォームやリンク）
- **PDE 版の時間感覚**: ホスティングは Vercel / Cloudflare で数分。時間をかけるのは「何を出すか」と「壊れたときにどうするか」の決定

## よくある失敗

1. **シークレットの公開**: .env の鍵がクライアントバンドルに含まれたままデプロイ
2. **レート制限・コスト上限の未設定**: AI API の従量課金が 利用者全員のリリース初日に爆発する
3. **エラーページのデフォルトのまま**: 404 / 500 が開発者向け表示のまま
4. **フィードバックの受け皿なし**: 利用者が困っても連絡する場所がない。改善ループの起点を自分で殺す
5. **一度に出しすぎる**: Must を全部入れて初リリース。どこが悪いか分からなくなる

## PDEの仕事

- **公開範囲の決定**: 誰に出すか（自分 / 友人 5 人 / 一般公開）。段階的な公開を選ぶ勇気
- **コストとレート制限の設定**: API プロバイダ側の上限設定、アプリ側のレート制限。**これを忘れると請求が現実になる**
- **切戻しの準備**: Vercel の instant rollback、直前のデプロイ URL を確認してから公開する
- **既知問題の明示**: 「今は動かないこと」を利用者に正直に書く

## AIツールの使いどころ

| 局面 | ツール | 使い方 |
|---|---|---|
| リリース前チェック | Claude Code | 「シークレット漏洩・SEO・404/500・OG 画像・レスポンシブを監査視点でチェック」させる |
| リリースノート | Claude / GPT | 変更履歴から利用者向けの説明を生成（自分の言葉で直す） |
| エラーページ | v0 / Cursor | 404 / 500 / メンテナンス画面のデザインと実装 |
| 監視設定 | Claude Code | Vercel Analytics / Sentry の導入と、見るべきメトリクスの設定案 |

## 進め方（実プロンプト付き）

### ステップ 1: リリース前の監査

```text
（Claude Code へ）このリポジトリを本番リリース前の監査視点でチェックしてください。
①シークレット: .env 参照がクライアントバンドル（NEXT_PUBLIC_）に漏れていないか
②エラー: 404 / 500 ページが実装されているか
③OG 画像・ファビコン・title/description が揃っているか
④API のレート制限・タイムアウト設定があるか
⑤利用者向けのフィードバック導線（メール / フォーム）があるか
指摘にはファイルと修正案を付ける。
```

### ステップ 2: コストと制限の設定

```text
AI API（例: Anthropic API）を一般公開アプリで使うときの安全設定のチェックリストを、
「設定箇所 / 推奨値の決め方」の表で出してください。
観点: 月額上限 / リクエストレート制限 / 1 リクエストの最大トークン / 異常検知の通知 / キャッシュ戦略
```

→ 出てきた表に沿って、API コンソールとコードの両方に設定を入れる。**設定した箇所をメモに残す**。

### ステップ 3: 段階的公開

```text
このアプリの公開プランを作ってください。
段階: ①自分 → ②知人 5 人 → ③一般公開
各段階で: 見るべきメトリクス / 確認すること / 次の段階へ進む条件
利用者数の想定: 現時点で 10 人程度。インフラは Vercel + 既存 AI API。
```

## 成果物と受け入れ基準

- 公開 URL、リリース前監査の記録、コスト設定のメモ、フィードバック導線

受け入れ基準:

- [ ] 監査でシークレット漏洩が 0 件
- [ ] API の上限・レート制限が設定済み（設定箇所を記録）
- [ ] 404 / 500 ページが自作され、OG 画像が設定されている
- [ ] 利用者から連絡できる導線（メール / フォーム）がある
- [ ] 既知問題がリリースノートに明記されている
- [ ] 切戻し手順（前バージョンへの戻し方）を 1 回リハーサルした

## 前後の工程との接続

- **テスト ←**: 監査で見つかった問題は「本番でしか見つからない系」。同じ種類の問題を次回の自動テストに足す
- **運用へ**: 公開した瞬間から運用が始まる。アナリティクスとフィードバックの見る習慣が、次の改善サイクルの燃料になる
