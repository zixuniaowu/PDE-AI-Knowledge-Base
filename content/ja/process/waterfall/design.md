## この工程の目的

設計は「要件を満たす解の構造を決める」工程。機能の一覧から、**変更に強く・壊れにくい構造**への変換を行う。要件定義が What なら設計は How と Where。

- **インプット**: 要件定義書（FR / 非機能要件 / 出所付き）
- **アウトプット**: アーキテクチャ図、インターフェース定義（API スキーマ）、データモデル、モジュール分割、**設計判断記録（なぜその案か）**
- **この工程が失敗したとき**: 実装は動くが変更に弱いシステムが出来上がる。要件変更 1 件で複数モジュールに波及する「設計の負債」は、コードレビューでは検出できない

## この工程特有の失敗（AI 以前からある問題）

1. **設計判断の記録漏れ**: 「なぜ B 案か」が残らず、1 年後に誰も理由を説明できない。すると安易な改修で構造が壊れる
2. **要件の文字面通りの設計**: 「CSV 出力」を要件通り作るが、背後の目的（経営資料を楽に）を設計に反映しない
3. **非機能要件の設計欠落**: 性能目標があるのにボトルネック箇所を設計で検討しない
4. **銀の弾丸探し**: 新しい技術で解決しようとして、制約（チームのスキル・運用負荷）を無視する

## 人間の役割

- **アーキテクチャの決定**: モノリス / マイクロサービス、DB 選定、非同期 / 同期。トレードオフは「チームが保守できるか」「運用体制に合うか」で決まり、この判断材料の一部（技術的新しさ・流行）には AI の知識が古い、あるいは一般論すぎて使えない
- **組織に合わせた構造決定**: コンウェイの法則——システムは組織構造を映す。4 人のチームにマイクロサービス 12 個は設計ではなく自殺。この判断は AI より人間
- **設計レビューの議長**: AI の指摘を採用 / 却下し、**却下理由も記録**する

## AIの役割

- 要件 → 設計項目の対応表作成（漏れの検出）
- 複数アーキテクチャ案の比較表のたたき台（ pros/cons は一般論として有用。最終判断材料）
- インターフェース定義・データモデルのドラフト（OpenAPI、ER 図のテキスト表現）
- 過去設計資料の検索（RAG）と整合チェック
- 設計レビュー観点のチェックリスト生成と一次指摘

## 協働の進め方（実プロンプト付き）

### ステップ 1: 比較案を作らせる（決めさせない）

```text
あなたはアーキテクチャ設計の補助です。次の制約条件下で、実現可能な構成案を 3 つ提案してください。
制約: 開発チーム 4 名（バックエンド 2、フロント 2、SRE 専任なし）/ 月次ピーク 10 万リクエスト / 予算は小規模
各案について: 構成図（テキスト）、長所 3、短所 3、月額インフラ概算、チームのスキルセットとの相性、
「1 年後に機能が 2 倍になったときの変更箇所」を出してください。
決定はしません。比較材料のみ。
```

### ステップ 2: 人間が選び、**理由を 2 行で記録**

選んだ理由を AI に書かせない。「B 案: SRE 専任がいないため運用負荷の低い構成を優先」のような、**その組織の事情が入った理由**は人間しか書けない。これが設計判断記録。

### ステップ 3: 詳細設計のドラフト → 人間がレビュー

```text
採用案（B 案）の詳細設計ドラフトを作ってください。
1. API インターフェース定義（OpenAPI 3.0 形式）: エンドポイント / リクエスト / レスポンス / エラー形式
2. データモデル（ER 図を Mermaid で）: 正規化の判断もコメント付きで
3. 非機能要件 FR-NF-002（応答 95%tile 500ms 以内）を満たすための設計上の工夫
要件定義書: （添付） 採用理由: （添付）
```

### ステップ 4: 設計レビューで AI を「新人レビューアー」にする

```text
あなたは設計レビューの補助です。この設計書を、以下の観点でレビューしてください。
観点: ①要件との対応漏れ ②インターフェースの不整合（名前・型・エラー） ③障害時の挙動が未定義の箇所 ④運用時に困る箇所（ログ・監視・デプロイ）
指摘には設計書の該当セクション番号を付ける。指摘しないこと（問題ないこと）の報告は不要。
```

## 成果物と受け入れ基準

設計書の実物に近い断片:

> **D-007 決定: 決済処理は非同期キュー経由とする**
> 理由: 同期 3 秒待ちでは FR-NF-002（95%tile 500ms）を満たせないため。キューは既存の SQS を再利用（新規ミドルウェア導入は運用負荷増のため却下 / 2026-09-13 確定、却下案: Kafka）

受け入れ基準:

- [ ] 全ての FR / 非機能要件に対応する設計項目がある（対応表で確認）
- [ ] インターフェースのエラー形式が統一されている（成功・失敗・タイムアウトの 3 種が定義済み）
- [ ] 重要な設計判断すべてに「理由 + 却下した案 + 日付」がある
- [ ] 障害時の挙動（外部 API が落ちたとき）が書かれている
- [ ] AI ドラフトの採用部分・修正部分のレビュー記録がある

## 工程間の受け渡しで壊れること

- **要件 ←（逆方向）**: 設計中に要件の曖昧さが見つかったら、設計側で解釈を固定せず**要件定義書に戻して修正**する。設計書だけで解釈すると、テストが要件と突き合わせできなくなる
- **実装へ**: 設計判断記録が実装に渡らないと、実装者が「なぜこうしたか分からないから最適化する」で構造を壊す。判断記録は実装者にも読ませる
- **テストへ**: 障害時挙動の定義はそのままテスト観点になる。書いていない箇所はテストも書かれない
