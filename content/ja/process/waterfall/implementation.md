## この工程の目的

実装は「設計を動くコードに変換する」工程——ではなく、正確には**「設計と現実のズレを発見し、設計を更新しながら動くものを作る」工程**。実装中に必ず設計の誤り・漏れが見つかる。それを黙って回避するのが最悪で、設計に戻して修正するのが正しいループ。

- **インプット**: 詳細設計書（判断記録付き）、コーディング規約、既存コードベース
- **アウトプット**: 動作するコード、テストコード、**設計との差分とその理由の記録**
- **この工程が失敗したとき**: 「動くが誰も読めないコード」が生まれる。AI 生成コードの普及で、この失敗はむしろ増えている

## この工程特有の失敗（AI 時代に加速した問題）

1. **理解していないコードのマージ**: 動くから OK。障害時に読める人がいない
2. **AI のもっともらしい実装**: 存在しないライブラリ関数、非推奨 API、言語の古い書き方を自信満々に生成
3. **設計からの黙認逸脱**: 設計にない例外処理・データ構造を「都合により」追加し、誰も記録しない
4. **テストの形骸化**: 「常に通るテスト」「アサーションなしのテスト」でカバレッジだけ稼ぐ
5. **巨大 diff**: AI に一気に作らせて、レビュー不可能な PR を出す

## 人間の役割

- **理解の責任**: マージするコードは全行理解していること。この基準を緩めると、チームの実質的なコード理解者がゼロになる
- **設計判断の持ち込み**: 認証・認可、個人情報の取り扱い、金銭計算（浮動小数点を避ける等）は人間が実装するか、実装を人間が精査する
- **設計へのフィードバック**: 実装中に見つかった設計の誤りを、勝手に回避せず設計書に戻す
- **規約・言語の現在地の把握**: AI が参照するのは学習データの言語バージョン。自プロジェクトのバージョン・規約を人間が管理して渡す

## AIの役割

- 設計書の該当セクションに基づく実装のたたき台（定型部・ボイラープレート中心）
- テストコードの下書き（境界値・異常系の候補列挙）
- リファクタリング案の提示（既存コードの重複検出など）
- 規約違反の事前チェック（人間のレビュー前のふるい）
- 「このコードを説明して」による理解の補助（※理解の代替にはならない）

## 協働の進め方（実プロンプト付き）

### ステップ 1: 小さく依頼する（関数・モジュール単位）

```text
あなたはこのリポジトリの実装補助です。以下の仕様の関数を実装してください。
条件:
・TypeScript 5.5 / Node 22。npm パッケージは既存の package.json の依存のみ使用（新規追加は提案のみ）
・既存ヘルパー src/utils/format.ts の関数を再利用する（重複実装しない）
・出力: {code, tests: [正常系2, 境界値2, 異常系2], assumptions: []}
・仕様で決まっていない点は実装せず assumptions に列挙する
仕様: 消費税込み価格の計算。税Rateは引数で受ける。丸めは四捨五入で小数第 1 位
設計書の該当箇所: D-012（金銭計算は整数演算）
```

### ステップ 2: 人間が「全行読む」— 読めない行はマージしない

読めない行があれば:

```text
この関数の 12〜18 行目の処理を、ライブラリの挙動レベルで説明してください。
なぜこの書き方でバグを避けられるのか、別の書き方との違いも含めて。
```

で説明させる。それでも理解できないなら**そのコードは使わない**。AI に書き直させるか人間が書く。

### ステップ 3: テストを「攻める側」に書かせる

```text
この実装のバグを探すテストを書いてください。動作確認ではなく、壊すことだけを目的に。
・境界値: 税率 0、価格 0、負の値、极大値
・丸め誤差: 0.1 の累積、少数の四捨五入の端数
・異常系: 引数 null、非数値
```

### ステップ 4: 設計との差分を記録する

```text
実装したコードと設計書 D-012 の対応を確認してください。
設計と異なる実装・設計に書かれていない判断があれば、
「設計の記述 / 実装の実際 / 差異の理由」の表で出してください。
```

→ 差異は設計書に反映して確定。**黙認逸脱を作らない**。

## 成果物と受け入れ基準

- 動作するコード + テストコード + 設計差分の記録

受け入れ基準:

- [ ] 全行を理解してレビューした人が 1 名以上いる（レビューアーの名前を記録）
- [ ] テストはアサーションを実質的に含む（「例外が出ないこと」だけのテストは無効）
- [ ] 金銭・認証・個人情報系のコードは人間が行単位で確認した
- [ ] 設計との差分リストがあり、設計書が更新されている
- [ ] 静的解析・規約チェックをパスしている
- [ ] PR の diff サイズはレビュー可能な範囲（目安: 400 行以内。AI に大きく作らせたなら分割）

## 工程間の受け渡しで壊れること

- **テストへ**: 実装者がテストも書くと「実装を証明するテスト」になりがち。テスト観点は設計の障害時挙動から独立に作り、実装のテストはその観点を満たすかで検収する
- **運用へ**: 実装時の判断（なぜこのリトライ回数か）が残らないと、障害時に「謎の定数」になる。判断はコードのコメントではなく設計書・判断記録に残す
