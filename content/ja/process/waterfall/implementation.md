## この工程の目的

PDE の実装は「AI に書かせる」ことではない。**「AI に書かせつつ、コードベースの品質と保守性に自分で責任を持つ」こと**である。AI ツール（Claude Code / Cursor / v0）は数分で数百行書く。だが生成物の構造・依存・セキュリティ・パフォーマンスへの責任は、コミットした人間にある。**「読めないコードは本番に入れない」は AI 時代こそ絶対ルール**。

- **インプット**: プロトタイプ（設計）、リポジトリ、選定済みスタック
- **アウトプット**: 本番稼働コード、テスト、デプロイ設定、**自分が説明できる状態**
- **PDE 版の時間感覚**: 書くのは AI のほうが速い。人間の時間は「確認・判断・統合」に充てる。作業配分の目安は 生成 20% : 確認と調整 80%

## よくある失敗

1. **生成コードを diff ごと受け入れる**: 「動いた」で accept。構造が破綻していても気づかない
2. **AI の技術選定に従う**: 存在しない / 非推奨のライブラリ、古い書き方を自信満々に採用してくる
3. **リポジトリの汚染**: 都度生成した類似コンポーネントが乱立し、スタイルが 3 種類混在する
4. **テストを書かせて満足する**: 「常に通るテスト」「アサーションが空のテスト」で安心する
5. **シークレットの漏洩**: .env の鍵や実データを AI のコンテキストに平気で貼る

## PDEの仕事

- **スタックとアーキテクチャの決定**: Next.js / DB / 認証方式の選定は人間。AI の提案は比較材料
- **コードレビューの実施**: AI の PR をレビューする姿勢で自分も読む。理解できない行は通さない
- **セキュリティと権限の実装判断**: 認証・認可・個人情報の扱いは、生成物を信頼せず行単位で確認する
- **構造の維持**: コンポーネントの分割、命名、ディレクトリ構造。生成物を後からでも整理してよい

## AIツールの使いどころ

| 局面 | ツール | 使い方 |
|---|---|---|
| 初期構築 | v0 / Claude Code | 認証付きの雛形を生成。ただし依存の選定は自分で確認する |
| 機能実装 | Claude Code / Cursor | 設計の状態一覧を渡して実装させる。1 PR = 1 機能で小さく回す |
| リアルタイム補助 | Cursor / Copilot | 書きながらの補完。括弧の外側（アーキテクチャ）は自分で決める |
| リファクタ・ review | Claude Code | 「この diff をレビューせよ」「脆弱性を探せ」を生成後に自分で実行させる |

## 進め方（実プロンプト付き）

### ルール: 小さく依頼 → 読む → 統合する

```text
（Claude Code / Cursor へ）
次の 1 機能だけを実装してください。
機能: 議事録の編集画面（生成済み議事録のテキストを編集、自動保存）
条件:
・スタック: Next.js 14 App Router / TypeScript / 既存の src/lib/db.ts を使用（新規依存は提案のみ）
・src/components/editor/ に配置。既存の Button / Input コンポーネントを再利用
・状態: 編集中 / 保存中 / 保存成功 / 保存失敗（再試行ボタン）
・出力は {files: [{path, code}], tests, assumptions} 形式。仕様にない判断は assumptions へ
・テストは正常系 2 / 境界値 2 / 異常系 2
```

### 生成後に必ずやる 3 件事

```text
1. 依存の確認: package.json の diff を見る。新規依存があれば「週次 DL 数 / メンテ状況 / 代替」を調べてから許可
2. 自力レビュー:
   「この diff をシニアエンジニアとしてレビューしてください。脆弱性・パフォーマンス・エッジケース・保守性の順で指摘。各指摘に重要度を」
   → 指摘が正しければ修正させる。これを通してから自分で最終確認
3. 理解チェック: 理解できない箇所が残ったら、その箇所は生成し直すか人間が書く
```

### セキュリティ関連は別枠で確認

```text
このアプリの認証・認可まわりのコードを監査視点で読んでください。
・未認証でアクセスできる API はないか
・他ユーザーのデータが参照できる箇所はないか（IDOR）
・クライアント側だけで権限を判断していないか
指摘にはファイルと行番号、攻撃シナリオを付ける。
```

## 成果物と受け入れ基準

- 本番環境にデプロイされたコード、テスト、そして「自分で説明できる」状態

受け入れ基準:

- [ ] 全ての依存追加を自分で確認・承認した
- [ ] AI 生成コードのセルフレビュー（AI 評 + 自分の目）の記録がある
- [ ] 認証・認可・個人情報系は行単位で自分が確認した
- [ ] テストは実質的なアサーションを含み、CI で自動実行されている
- [ ] 同じ用途のコンポーネントが重複していない
- [ ] コミットメッセージ・PR 説明に「AI 生成 + 人間確認」の事実が残っている

## 前後の工程との接続

- **設計 ←**: 実装中に「この状態、設計で抜けてる」と気づいたら実装側で埋めず、状態一覧に戻して追加する（solo だからこそ、文書を現実に合わせて育てる）
- **テストへ**: 自分の環境では通る。次は他人の環境（実ユーザー）で壊す——テスト工程へ
