理論は[ガイド](/guide/what-is-pde)と[パターン](/patterns)に譲って、ここは**貼ってすぐ動く形**だけを集めました。気になるところから拾って使ってください。

## 基本の型

### 1. 役割 + 目的 + 制約の 3 点セット

いきなり「〜を書いて」より、この 3 行の枠に入れるだけで出力が安定します。

```text
役割: あなたは中小企業向けの研修資料を作る編集者です
目的: 新入社員向けの「報連相」説明資料の目次を作る
制約: 専門用語は使わない。1 見出し 20 字以内。項目は 5〜7 個
```

### 2. まず確認させてから作業させる

いきなり出力させず、**理解の確認を 1 往復させる**と手戻りが激減します。

```text
作業を始める前に、以下を確認してください。
・私の依頼で曖昧な点を 3 つ質問する
・理解した内容を 3 行で復唱する
・私が「OK」と言ったら作業を開始する
```

### 3. 出力形式を先に指定する

形式を指定しないと、AI は毎回違う形で返します。表やチェックリストにするなら最初に言う。

```text
出力は次の表形式で。他の文章は付けないでください。
| 課題 | 現状 | 対策案 | 優先度(高/中/低) |
```

### 4. やらないことを伝える（否定形の制約）

「〜して」より「〜するな」のほうが効くことが多い。禁止リストを明示する。

```text
・点数は提案しない（達成度の判定まで）
・「素晴らしい」「残念ながら」などの評価語で始めない
・推測で書かない。書けない箇所は [不明] と出す
```

## 品質を上げる

### 5. 例を 2〜3 個見せる（Few-shot）

説明より例。**バリエーションを変えて 2〜3 個**渡すのがコツ（1 個だとその癖を真似る）。

```text
次の例と同じ粒度・トーンで出力してください。

例1:
入力: 「発送が遅れてるみたいだけど大丈夫?」
出力: {種別: 配送遅延の問い合わせ, 緊急度: 中, 要返信: はい}

例2:
入力: 「先日はありがとうございました。また機会があれば」
出力: {種別: 感謝の連絡, 緊急度: 低, 要返信: いいえ}
```

### 6. 根拠の引用を必須にする（ハルシネーション対策）

根拠を義務づけると、もっともらしい嘘を構造的に防げます。

```text
各項目について、根拠となる原文の該当箇所を必ず引用してから回答してください。
原文に根拠がない項目は「根拠なし」と明記してください。推測で補完しないでください。
```

### 7. 自分でチェックさせてから渡させる

人間に見せる前に、**受け入れ基準で自己点検**させると、指摘対応の往復が減ります。

```text
出力の後に、次のチェックリストで自己点検してください。
□ 全ての主張に出典がある
□ 指定した 5 項目をすべて含む
□ 文字数は 800 字以内
不合格の項目があれば修正してから、修正版だけを出力してください。
```

### 8. 「分からないことは分からないと答えさせる」

AI は無理に答えがち。逃げ道を用意すると誤答が減ります。

```text
確信が持てない内容には「分かりません」と答えてください。
推測で答えるより「分かりません」のほうが価値があります。
```

### 9. 案を 5 個出させてから選ばせる

最初の 1 案は平凡になりがち。**量を出させてから選ぶ**ほうが質が上がります。

```text
キャッチコピーを 5 案出してください。それぞれ違う切り口で（安心感 / 数字 / 疑問形 / 比喩 / 率直さ）。
最後に、あなたが一番おすすめする 1 案と理由を 1 行で添えてください。
```

### 10. 難しい作業は手順に分解させる

大きな依頼は途中で指示を忘れます。段階に分けて、各段階で自分を止めさせる。

```text
次の順番で作業し、各ステップの出力を私が確認してから次に進んでください。
STEP1: 資料から課題を 10 個抽出する
STEP2: 類似度で 3 グループに分類する
STEP3: グループごとに改善案を 1 つずつ提案する
```

## 文書・文章の小技

### 11. 一言要約 → 詳細の 2 段階出力

長い文章をいきなり読まされるのを防ぎます。

```text
まず全文の要約を 3 行で出してください。私が「続き」と言ったら、
見出し付きの詳細版を出してください。
```

### 12. 読み手になりきって添削させる

書き手のままでは気づかない問題を、**読み手の立場**でチェックさせます。

```text
この文章を「初めて読む新入社員」の立場で読み、
・意味が分からなかった箇所
・行動に移せない箇所
を箇条書きで指摘してください。修正案はまだ書かないでください。
```

### 13. 直すときは全文書き直しさせない

「書き直して」だと良かった部分まで変わります。**差分指示**にする。

```text
全文を書き直さず、以下の 2 点だけを修正してください。他の部分は 1 字も変えないでください。
① 冒頭に結論を 1 文追加
② ③ の段落の数字を出典付きに変更
```

### 14. トーンを揃えるには自社の文章を例として渡す

「丁寧に」の解釈は人それぞれ。**実物の例**が一番の仕様書です。

```text
添付の過去メール 2 通と同じトーンで、返信文案を 3 案作ってください。
（例: 謝罪の言葉は 1 回だけ / 「ご確認いただけますと幸いです」系の表現を使う 等）
```

## コード・データの小技

### 15. エラーは「期待 vs 実際」で貼る

エラーメッセージだけ貼るより解決が早い。この型で貼るのが一番伝わります。

```text
次のバグを直してください。
・期待した動作: 送信ボタンで API が 1 回だけ呼ばれる
・実際の動作: 2 回呼ばれる（ネットワークタブの記録を添付）
・エラーメッセージ: （貼付）
・環境: React 18 / 独自の hooks なし
原因の候補を 3 つ挙げてから、最も可能性の高い修正案を出してください。
```

### 16. コードにはテストも一緒に書かせる

テストがあると「動くと思い込み」を機械的に防げます。

```text
この関数の実装と、テストコードを一緒に出してください。
テストは正常系 2 件、境界値 2 件、異常系 2 件を含めてください。
```

### 17. 数値は「渡して解説させる」だけ。計算させない

LLM は計算を間違えます。**数値は表計算やシステムから**、AI は解説だけ。

```text
以下の数値表の解説文を書いてください。
ルール: 計算・合計・割合の新規算出は禁止。表にある数値のみを使い、
数値を書くときは「表の○行」のように出典を括弧で添える。
（表を貼付）
```

## 日々の運用

### 18. うまくいったプロンプトは保存して「型」にする

毎回ゼロから書くのが最大のムダ。使えたものは変数だけ替えて再利用します。

```text
（保存例: 採点補助の型）
あなたは高校数学の採点補助です。
・ルーブリックに基づき、設問ごとに達成度と根拠の引用を出力
・点数は提案しない
・フィードバックは 3 文以内、否定語で始めない
【変数】ルーブリック: {ここ} / 答案: {ここ}
```

### 19. 機密情報は仮番号化してから渡す

入力の前に 1 分の置換で、情報漏洩リスクをほぼゼロにできます。

```text
（渡す前に置換）
患者 3 名 → 患者 A / 患者 B / 患者 C
顧客名 → 顧客 X 社
金額 → 【確定待ち】
※ 対応表は自分の手元にだけ残す
```

### 20. 改善履歴を 1 行メモで残す

プロンプトは文章と同じで改訂して育てます。何が変わったかだけ残す。

```text
（プロンプトファイルの末尾に追記していくメモ）
2026-09-01: 出力形式の指定を追加 → 表崩れがなくなった
2026-09-10: 「点数を出さない」制約を追加 → 教師の最終判定が明確になった
```
